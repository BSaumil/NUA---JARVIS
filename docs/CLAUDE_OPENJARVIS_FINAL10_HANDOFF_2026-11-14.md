## Workstream status

### Workstream 2 — Presence Mesh companion pairing client (Android)
**Status: SHIPPED_BUILDABLE_NOT_DEVICE_VERIFIED**

`app/src/main/java/com/nua/assistant/presence/companion/`: `CompanionIdentity`
(BouncyCastle Ed25519 — minSdk 26 predates platform EdDSA, which Conscrypt only
added at API 33), `CompanionSecurity` (canonical request / digest / nonce /
compact-JSON, mirroring `services/companion/nua_companion/security.py`
field-for-field), `CompanionPairingClient`, `CompanionApiClient`,
`CompanionTransport` (real OkHttp + a fake for unit tests).

Verified: `CompanionSecurityTest` checks digest/compact-JSON/signature output
against **golden vectors generated by running the actual
`nua_companion.security` module** against fixed inputs — a genuine
cross-language interop proof, not a round trip against itself. This caught a
real bug before it shipped: the first `compactJson` implementation didn't
escape non-ASCII text the way Python's `json.dumps(ensure_ascii=True)` does,
which would have broken every signature on a non-English prompt.
`CompanionPairingClientTest` / `CompanionApiClientTest` cover orchestration
logic against a fake transport; `CompanionOkHttpTransportTest` covers the real
HTTP plumbing against MockWebServer.

Not verified: an actual pairing handshake against a running companion from a
real Android device/emulator (no Android build environment in this sandbox —
see "Environment constraints" below), and the production Hilt wiring (no
`AppModule` binding for `CompanionHttpTransport`/`CompanionIdentity` was added,
since there's no UI surface yet to inject them into).

**Known protocol discrepancy, not yet resolved:** this workstream's wire
format (raw 32-byte SHA-256 digest, signed directly) is *not* the same
convention as `localapi/LocalApiContract.kt`'s `localApiRequestDigest`, which
returns a **hex string** digest instead. Both were reused/mirrored correctly
for their own surface (companion-node HTTP API vs. the Local API contract),
but they are two different canonicalizations living in the same codebase.
Recommend ChatGPT/a future pass decide whether `LocalApiContract.kt` should
gain a raw-bytes digest variant, or whether the companion's own protocol
should be formally folded into the Local API contract — not done here to
avoid redefining a canonical ChatGPT-owned type unilaterally.

### Workstream 7 — Sandboxed Computation / WASM (Android half)
**Status: SHIPPED_BUILDABLE_NOT_DEVICE_VERIFIED**

`app/src/main/java/com/nua/assistant/sandbox/wasm/`: submits a computation via
`SandboxTransport` (real implementation is the companion client above) and,
if the result proposes an `ActionPlan`, routes it through the real
`WorkflowExecutor`/`CapabilityRegistry` — never creates a side effect itself.
An unknown action string, or a real `NuaActionType` with no registered
capability, refuses the **whole** plan, never just that step.

The companion-side WASM runner itself (`services/companion/nua_companion/
sandbox.py`) is ChatGPT's and was already real/tested before this session
(`wasmtime`-based, refuses any module with imports, enforces fuel/memory/
wall-time limits) — not re-verified here, only consumed.

7 unit tests verify: computed-only results never touch the executor; a real
registered action actually runs; a confirm-required action (e.g. `SMS_SEND`)
is never auto-executed; an unknown action name and a real-but-unregistered
action are both refused wholesale; transport failure is reported honestly;
the idempotency key is derived from program digest/export/input, not random.

**What is actually verified, for real, locally, in this sandbox:**

signed-payload rejection, and a two-device confusion case. Run together with

In writing that integration test, found and fixed a real bug in
`services/companion/nua_companion/service.py`'s `/inference` handler: it read
`modelId`/`prompt` from unsigned top-level request fields instead of from the
signed `payload`, so a request's Ed25519 signature didn't actually cover what
the handler would act on — a tampered prompt with a valid signature from an
approved device would have executed. Now reads exclusively from `payload`.

## Environment constraints (apply to every Kotlin/Android change above)

This sandbox's egress proxy blocks `dl.google.com` (Google's Maven repo,
required for AGP/AndroidX) by policy — confirmed via the proxy's own status
endpoint and `/root/.ccr/README.md`'s explicit guidance not to route around a
policy denial. So **no Android/Kotlin code in this handoff was compiled
locally**; verification rests on (a) unit tests reasoned through carefully by
hand, (b) cross-language golden vectors generated from the real Python
implementations where a wire format is shared, and (c) GitHub Actions CI,
which *does* have access to `dl.google.com` and is the actual source of truth
for whether this compiles. One real compile failure was caught and fixed this
way (`ResearchSourceProvider.kt`'s `orEmpty()` — see above) — proof the CI
loop is doing real work, not rubber-stamping.

By contrast, Maven Central and PyPI *are* reachable from this sandbox, so all
Python work (`services/companion`, `shared/protocol-consumers/python`) was
genuinely run and tested locally, not just reasoned about.

## Safety-boundary review (self-check against the directive's core rule)

"NUA may improve itself automatically. NUA may not silently grant itself new
authority." Checked against every addition above:

- The sandbox/WASM client (workstream 7) cannot create a side effect itself;
  every proposed action goes through the real, unmodified `WorkflowExecutor`
  and `CapabilityRegistry`, with per-step authorization exactly as already
  governed. An unregistered or unknown action refuses the whole plan.
- The companion pairing client (workstream 2) cannot approve its own pairing;
  `owner_approve` only exists on the companion side and is never called
  automatically by anything added here.
- The `/inference` signature-binding fix *tightens* an existing boundary (a
  signature now actually covers what gets executed) rather than loosening
  anything.
- The new connectors (workstream 4) are read-only, declare no write
  capability, and so have no UAF `REMOTE_TOOL` surface at all.
- No secrets, signing keys, or device-validation results were fabricated
  anywhere in this work. Where external verification (device pairing, a real
  compile, a built binary) wasn't possible in this sandbox, it's labeled
  `SHIPPED_BUILDABLE_NOT_DEVICE_VERIFIED` or `DEFERRED_PLATFORM_LIMITATION`
  above rather than claimed as done.

No `BLOCKED_CRITICAL` items from this workstream set.
